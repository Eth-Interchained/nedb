## The contract

Apples to apples means every engine gets the same work and is held to the same answer:

- **Same data.** One seeded dataset, handed byte-identical to every engine.
- **Same questions, same count, same order.** Each engine answers in its own idiomatic best form (SQL JOIN, `$lookup`, neSQL, or — for Redis, which has no join — a pipelined application-side join).
- **Same audit requirement.** *Keep every past version of an order, and answer what the data looked like before the refund wave.* NEDB does this natively. Every other engine gets it the way it is built in production — a history table in the same transaction, a history collection in a multi-document transaction, a history list inside `MULTI/EXEC` — and pays for it in the write path and in the query.
- **Same oracle.** Every answer is checked against the value computed from the seed in plain Python. A wrong answer fails the run. No engine is scored on a result it got wrong.
- **Matched durability, not shipped defaults.** `durable` = every commit on disk before the ack; `relaxed` = each engine's bounded (~1 s) loss-window mode. A leg that cannot honour a profile is **N/A**, never quietly run in a weaker mode.
- **Same client and machine.** One Python client process, one runner, engines run one after another. No foreign-key constraints on any engine, so none pays an integrity cost the others skip.

## Notes

¹ **NEDB (nedbd HTTP) / durable:** nedbd acknowledges a write before its index entry is fsynced and exposes no per-request flush, so it cannot honour 'on disk before the ack'  

## What this does and does not show

- Numbers are comparable **within one run**. GitHub runners are shared VMs; across runs, expect noise.
- Every engine is driven from Python, so client-side decode cost is in every number, for every engine alike.
- Embedded engines (NEDB embedded, SQLite) pay no socket hop. Compare them with each other, and compare the networked legs with each other — the tables are grouped for that reason.
- The point-in-time queries on the other engines assume no orders are inserted after the marker, which holds for this workload. NEDB's `AS OF SYSTEM TIME` has no such assumption.
- Re-run it yourself: **Actions → Benchmark (head-to-head) → Run workflow**, or locally with `python3 bench/compare.py --orders 5000 --markdown /tmp/BENCHMARKS.md` (unreachable servers are skipped, loudly).
